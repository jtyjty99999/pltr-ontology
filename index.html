Chapter 01引子：AI 落地为什么总差一口气

先看三个每天都在发生的场景。它们看起来毫不相干，但缺的是同一样东西。

场景一

BI 只会告警，不会决策

营收连续三个月下降，BI 弹出告警。然后呢？然后经营团队开三天会，把供应链流程从头梳理一遍才能定出动作。分析决策发生在系统外。

场景二

系统只录结论，不给结论

关键物料供货中断时，引入替代物料、调货、还是调安全库存？系统有三个功能，但不告诉你用哪个。真正做判断的是那个做了十五年的老采购员。

场景三

大模型能说，但数字靠不住

问它「上季度毛利为什么掉 3 个点」，它写得出漂亮报告 —— 但数字是编的。给它数据库，它算错；给它语义，它天马行空。

问题的公共内核

把三个场景抽象一下，会看到同一个空缺：

场景与问题  →  【思考与决策过程】  →  系统里的操作结果
                    ↑
              这一段，现在是人在做

传统 IT 建设把端到端流程分而治之，拆进了 ERP、SCM、CRM 一个个功能点里。结果是：系统里没有一个叫「端到端流程」的功能，也没有任何地方写明业务功能是如何支撑业务流程的。

关键结论 AI + 本体要解决的，既不是「场景问题」，也不是「系统录入」，而是这两者之间那个被跳过的「分析与决策」。

要让 AI 接住这一段，它需要两样东西：

  1. 一份完整的业务语义 —— 业务对象是什么、彼此怎么关联、一个动作会引发什么连锁反应；
  2. 一个决策认知框架 —— 有经验的人是怎么想这个问题的，方法论本身。

这两样东西的载体，就是本体模型。

Palantir 的定位：不生产水，做水的搬运工

它早期是一家做数据集成的公司 —— 不是主数据，不是数据中台，不是传统 BI。它要做的不是实现一个业务系统功能，也不是实现一个数据中台的指标，而是把你游离在系统外的经验建模、显性化，结合已有系统的数据与大模型的推理能力，帮你做分析决策。

常见误解实际情况
它是 BI 公司不是。早期核心是数据集成
它是数据中台不是。企业已有中台，它可以对接；没有，它可以连中台带分析一起建
它要替换你的 ERP不。它最大化保留你已有的 OLTP / OLAP 资产，在两者之间架桥
它自己执行业务流程不。它不直接参与业务和流程，是在系统外挂一层

由此推出一个反直觉的判断：「回写」不是重点。把改进建议写回源系统本身没有任何技术含量。真正的重点是 模型 + 数据 + 大模型推理 → 得出比有经验员工更优的改进建议。

本体论不是万能的。很多精确化的问题，不需要本体就能很好地解决。

企业要上本体论，先问自己：日常业务里有哪些痛点，是传统 IT 应用难以解决的？有哪些是 AI 赋能时因为幻觉太重而无法满足的？有哪些是极度依赖有经验员工才能解决的？

这些，往往才是需要「本体模型 + AI」的关键点。

Chapter 02本体论是什么

哲学源头：Ontology 本来在问什么

「本体论」的词根是希腊语的 on（存在）与 logos（道 / 学）。它讨论的不是「世界是什么样的」，而是更底层的问题：「存在」本身意味着什么？

阶段代表核心主张
起点巴门尼德「存在者存在，不存在者不存在」—— 第一次把「存在」当作可思考的对象
奠基亚里士多德《形而上学》研究「作为存在的存在」，提出实体、范畴、四因说
转折笛卡尔 / 康德从「世界是什么」转向「我何以能认识世界」
集大成海德格尔《存在与时间》重提「存在的意义」问题，指出两千年本体论遗忘了存在本身

这条线索可以整理成「奠基者 → 集大成者」的三组对照：

领域奠基者集大成者核心问题
逻辑亚里士多德黑格尔思维如何有效地推演
认识论培根康德我们如何认识世界
本体论巴门尼德海德格尔存在本身是什么

两个核心研究点 —— 它们正是工程化本体论的钥匙

研究点一

区分「存在」与「本质」

一件事物「存在」是一回事，它「是什么」是另一回事。

→ 工程上：实例（Instance）与类型（Type）是两回事。

研究点二

区分「存在本身」与「存在者」

「存在」是持续发生的过程，「存在者」是这个过程中显现出来的东西。

→ 工程上：行为 / 事件（过程）与对象状态（结果）是两回事。

记住这两条 —— 后面讲「行为模型和事件模型为什么必须拆开」「为什么需要场景模型」时，你会发现它们是同一个洞见在工程层面的两次落地。

本质能不能被触达？三种立场，三种期待值

立场代表主张工程隐喻
有本质，且可触达柏拉图、黑格尔本质客观存在，理性可以把握可以建出完备本体，推理机能推出所有真理
有本质，但不可触达康德物自体不可知，只能认识现象本体只能逼近业务真相，永远是模型而非现实
根本没有本质奥卡姆、萨特只有个别事物，「本质」只是名字本体就是一套约定俗成的命名系统

这三者不是学术花边，它们直接决定你对本体的期待值。站在柏拉图那侧，你会觉得「模型没建全」是失败；站在康德那侧，你会接受「模型永远不完备，但足够好用」。一条重要的工程戒律正是后者的推论：本体要「精确」，但不必「完备」。

海德格尔《存在与时间》：概念 → 工程翻译

哲学概念一句话解释翻译成工程语言
存在论差异存在 ≠ 存在者，二者不能混为一谈类型系统 ≠ 实例数据；Schema ≠ Data
此在（Dasein）唯有人的存在会追问自己的存在系统的使用者 / 决策者，不是被建模的客体
上手状态工具顺手时你是「忘我」地在用，不觉得它是个东西好的系统是「透明」的，用户感觉不到系统
现成状态工具坏了你才停下来「看」它系统出问题、报表对不上时，模型才被审视
因缘整体性工具从不孤立，它处在「为了…而…」的关联网中对象从不孤立，它处在一张关系与目的之网里
时间性人同时活在既有处境、未来可能和此刻决断中数据的历史态、计划的未来态、决策的当前态
向死而生有限性让选择变得紧迫、真实资源约束与截止期限，才让「优化」有意义
常人 / 沉沦日常中我们按「大家怎么做」活着组织里的路径依赖与行业惯例
畏（Angst）一切意义悬空时的基本情绪模型失效、范式转换时的失重感
先行的决断直面有限性后做出的本真选择在不确定中依然下判断 —— 这正是决策的本质
解蔽（Aletheia）真理是「去蔽」，是把被遮住的东西露出来分析的本质：把隐藏的因果揭示出来
一句话概括 海德格尔告诉我们，「存在」不是一个静态的名词表，而是一张因缘关联的网络 + 一个时间性展开的过程。 如果一个本体模型最后是一棵树，那它在哲学上就已经错了 —— 更不用说在工程上。

信息科学的本体论：一句被引用最多的定义

1998 年 Studer 等人给出了至今最常被引用的定义：

本体是「共享概念模型的明确的形式化规范说明」。
要素含义工程上要问的问题
概念化对世界的一种抽象模型你打算把业务世界的哪些侧面建进来？
明确概念和约束都被无歧义地定义你的「订单」和财务的「订单」是同一个吗？
形式化机器可读、可处理是画在图上的图，还是能被程序解析的文件？
共享是共识，不是个人的业务方、开发方、AI 用的是同一套词吗？

「共享」这一条最容易被忽略，也最要命。一个只有建模者自己能看懂的模型，不是本体，只是笔记。

TBox 与 ABox：本体和知识图谱到底什么关系

这是初学者最容易混淆的一对概念。

TBox（Terminological Box）ABox（Assertional Box）
内容概念、属性、关系、公理具体的实例与断言
别名模式 / Schema / 本体数据 / 实例 / 知识图谱
例子「订单是一种单据，订单有客户」「订单 #10086 属于客户张三，金额 12,000」
谁定人（领域专家 + 建模者）系统运行中产生
变化频率慢，版本化管理快，持续写入

一句话：本体是「模具」，知识图谱是「用这个模具压出来的零件」。

一个反复出现的失败模式 很多人号称在做本体建模，最后交付的其实是一棵目录树（一级分类 → 二级分类 → 三级分类），而不是一张互相约束的网。 树状结构用传统的面向对象建模就够了，不需要本体。只有当你建出的模型里，对象、行为、规则彼此影响、彼此制约，形成闭环回路，后面的 AI 推理才有意义。

Chapter 03经典工具栈：能做什么，卡在哪

理解 Palantir 之前，必须先理解它绕开了什么。否则你会掉进「用 OWL 去解释 Palantir」的方法论陷阱。

工具栈全景

层标准 / 工具干什么
数据模型RDF、RDFS用「主语-谓语-宾语」表达事实；定义类与属性的基本层级
本体语言OWL / OWL 2类、对象属性、数据属性、个体；支持公理与形式语义
OWL 2 子语言EL / QL / RL 三个 Profile用表达力换推理效率：EL 适合大本体，QL 适合查询重写，RL 适合规则引擎实现
高级特性属性链 Property Chain例：hasParent ∘ hasBrother → hasUncle（父亲的兄弟是叔叔）
规则SWRL在 OWL 之上写「如果…则…」，能推导出新事实
约束校验SHACL（2017 W3C 推荐标准）闭世界下的形状约束；支持 SHACL-SPARQL 写复杂规则
查询SPARQL面向 RDF 图的查询语言
序列化Turtle / RDF-XML / JSON-LD人读用 Turtle，机器交换用后两者

一个容易被忽略的结构性矛盾：OWA 与 CWA 并存

OWA · 开放世界假设

没说的事就是「不知道」，不是「不存在」。我暂时不知道张三有兄弟，不代表他没有。

服务于逻辑完备性 —— 这是 OWL 的默认立场。

CWA · 封闭世界假设

没说的事就是「不存在」。数据库里没有这条记录，就是没有。

服务于校验与查询 —— 这是 SHACL 和 SQL 的立场。

经典工具栈里，这两套互相冲突的假设同时存在。这不是设计缺陷，而是两拨人为了解决两类不同问题各自做的选择，最后被拼在了一起。理解这一点，你就理解了「经典栈为什么在落地时总拧巴」。

推理的两副面孔

演绎推理 Deduction溯因推理 Abduction
方向一般 → 特殊结果 → 最可能的原因
形式所有人都会死；苏格拉底是人 → 苏格拉底会死草地湿了 → 大概下过雨（也可能是洒水器）
结论性质必然，逻辑上可证明或然，带置信度，可被推翻
典型载体OWL 推理机、SWRL、Datalog诊断、根因分析、假设生成
对应 AI符号主义、专家系统大模型的强项
错位在哪里 经典本体论的主战场是演绎；而企业真正需要的决策，大多是溯因。这个错位，是后面一切范式断裂的根源。

工具选型对照

工具定位优势短板
Protégé本体编辑器（斯坦福）免费、生态好、OWL 支持完整、DL 推理机可插拔面向静态本体；SHACL 支持弱；不做数据集成；不产生应用
GraphDB原生 RDF 三元组库内置推理机，支持前向 / 后向链；SPARQL 完备只解决「存 + 推 + 查」，行为 / 场景 / 应用层空白
Neo4j属性图数据库图遍历性能极佳、生态成熟、开发者体验好不原生支持 OWL/SWRL，语义推理需中间件补齐；本质是图存储不是本体平台

经典栈的四个结构性困境

  1. 落地鸿沟。纯 DL 本体很难直接对接生产数据流。OWL 的公理严谨性和「与真实数据库表 / API 直接映射」之间存在天然阻抗。Palantir 的解法是：牺牲公理严谨性，换来与真实数据源的直接映射能力。
  2. 假设冲突。OWA 与 CWA 同栈并存，导致「同一个模型，推理机说一致，校验器说违规」这类问题反复出现。
  3. 只有名词，没有动词。OWL 描述世界是什么样的；但业务的本质是发生了什么、应该做什么。行为、事件、场景、流程在经典栈里没有一等公民的位置。
  4. 范式失配。OWL/SWRL/SHACL 是为「封闭的、可公理化的语义系统」设计的，其设计哲学本身就排斥「允许置信度的动态推理」。这不是能力不足，是设计目标不同。
一个尖锐的判断 用经典本体论工具栈去逆向解释 Palantir，是一种方法论上的时代错位（anachronism）。 Palantir 绕开这套工具栈，不是因为他们不懂 Description Logic，而是因为 DL 推理机制本身就不是为这种混合场景设计的。
但是 —— 另一面同样重要 即使在 AI 大模型下有新的本体应用范式，对传统的经典做法也必须了解清楚。不理解 OWL / SWRL / SHACL 的边界在哪，你就无法理解 Palantir 为什么那么设计。

Chapter 04Palantir 的三层结构与范式断裂

三层结构

这是理解 Palantir 最核心的一张框架图。

层回答的问题核心构件沉淀的是什么
语义层业务世界里有什么Object Type、Object Instance、Property、Primary Key、Link Type、Object Set业务对象与关系（名词）
动能层业务上做什么Action Type、Function、Workflow State原子操作与计算（动词）
动态层怎么做最好Scenario、Workflow & Automations、模拟与比对经验、方法论、决策框架
 
语义层  定义业务世界（有什么）
   ↓
动能层  驱动业务操作（做什么）
   ↓
动态层  优化业务决策（怎么做最好）
最关键的洞察 真正最核心的「本体知识经验层」在动态层 —— 也就是企业知识管理里说的核心经验、模式和方法论。 当动态层积累得足够多时，对 FDE（前置交付工程师）的依赖就越小，本体模型本身也就越具备自我进化、面对从未出现过的新场景「举一反三」的能力。

语义层构件速查

构件含义类比
Object Type对象类型（业务概念）类 / 表结构
Object Instance对象实例一行数据 / 一个个体
Property属性（带业务语义，不是裸字段）字段
Primary Key对象的唯一标识主键
Link Type连接两个 Object Type 的关系类型外键 / 图的边
Object Set对象集合，可作为分析和操作的输入一个查询结果集

动态层：Scenario 沙箱推演

Scenario 是一个在本体数据基础上创建的独立分支或沙盒。用户和 AI Agent 可以在里面自由模拟各种操作或变化（调整价格、改变供应链、切换供应商），观察其对整个业务模型的影响，而完全不触碰真实数据。可以应用一系列预定义的 Action 模拟不同策略，并并排比较结果，确定最优解。

从分析到固化，走三步：

步骤做什么载体
1 · 探索与验证在沙箱里用 Action + Function 做自由 What-if 分析，找到最优解Scenario
2 · 抽象与模板化把验证有效的逻辑抽象出来Pipeline Builder 自定义函数；Workshop 保存 Scenario
3 · 编排与自动化把模板化的逻辑模块编排成端到端流程Workflows & Automations

保存下来的 Scenario 不依赖创建它的应用模块，可以在任何其他模块中加载复用 —— 相当于给分析结论建了一个快照。

为什么这一步如此关键 Palantir 的本体论并非让 AI 在空白画布上自由发挥，而是先由领域专家和工程师共同绘制一张精确的「业务地图」（本体），设定好「交通规则」（Action / Function）。AI 和人类用户在这张地图上做沙盘推演，所有行动都受地图和规则约束。这种设计确保 AI 的决策可解释、可控制、符合业务逻辑，而不是一个不可预测的黑盒。

它更像 OOAD / DDD，而不是 OWL

静态建模层面，OWL 的 Class-Property-Relationship 与 Palantir 的 Object Type / Property / Link Type 几乎同构，都和 OOA 的类图高度相似。区别在两点：

  1. OWL 有公理化的推理能力（子类传递、属性链、一致性检查），走的是 Description Logic 路线；
  2. Palantir 的 Object Type 更像一个「打了类型标签的数据库视图」，语义主要靠 Property 的命名和文档承载，背后没有强制的逻辑推理引擎在做开闭世界假设的演算。

结论：Palantir 在静态建模层面做了简化和工程化妥协 —— 牺牲 OWL 那种公理严谨性，换来与真实数据源的直接映射能力。

Action 与 Function 补上的两个「动词」

维度传统 UML 用例Palantir Action Type
性质文档性、描述性可执行、有副作用
前置条件文字描述绑定：谁能做、什么状态下能做
执行逻辑无绑定：改变哪些 Object 的哪些 Property
后置无触发 Function 链

更准确的定位：Action 是「事件驱动架构里的 Command / Event，套了一层用例的外壳」。它把 OOA 里偏静态文档化的用例，变成了本体图谱上可以直接触发状态迁移的节点。

Function 的两副面孔 —— 一个常被忽略的「语义断层」

类型例子性质可解释性
派生属性计算「合同已开票金额 = Σ 发票金额」声明式，像规则引擎 / SHACL 规则扩展 / Drools 前向链可解释、可追溯血缘
复杂业务逻辑 / 集成调用调用支付网关、跑复杂优化算法图灵完备的代码，只是挂在了本体的节点位置上黑盒，可推理性已退化为普通函数调用

一旦引入第二类，Function 就不再是「从本体结构里可推导」的东西了。表面上它是本体的一部分，实际上它的可解释性、可推理性已经退化成普通函数调用。由此得到一条非常实用的判据 ——

本体能力衰减梯度

事件语义、状态迁移

可解释、可追溯

越往右，本体语义越稀薄。做架构评审时，问一句「你这个能力挂在哪一档」，比问「你有没有本体」有用得多。

范式断裂：从「推理主体」到「上下文供给者」

经典本体论路线Palantir 混合路线
链路概念建模 → 公理约束编码 → DL 推理引擎演绎 → 一致性校验 → 静态知识图谱本体语义层 → 确定性 Function → 知识图谱检索 → LLM 生成编排 → 融合输出
推理主体推理机（单一主体）没有单一主体，三种异质能力拼接
哲学根基开放世界假设 + 公理化完备性三种认识论立场的工程化共存
结论性质逻辑上可证明、可解释、可回溯混合：精确 / 结构化 / 概率生成
本体的角色推理主体 —— 自己就是答案的来源上下文供给者 —— 提供结构约束和语义骨架

右侧链路里三种能力的职责切分

置信度 · 零

确定性计算

Function / 传统算法。SQL、统计算法、优化器。纯精确。

置信度 · 结构化

检索式推理

基于知识图谱的关联查找、路径查询。有一定模糊匹配空间。

置信度 · 动态

生成式推理

LLM 基于上下文的归纳、类比、常识补全。真正的「允许置信度」部分。

一个角色反转 传统认知是「本体是结构，LLM 在结构上做推理」。但 Palantir 的真实运作机制是：LLM 做的不是本体推理，而是 Function 调用的编排（orchestration）。 LLM 负责理解意图 → 决定调用哪个 Function / 查询哪个 Object → 把结果组织成自然语言。精确计算这部分完全不经过 LLM 的「推理」，而是确定性代码执行后把结果喂回去。
Palantir 的本体不是用来被推理引擎「推」的，而是用来被 LLM 和算法「查」和「算」的。 它的角色从「推理主体」降级为了「上下文供给者」。

这个降级不是缺陷，反而是让本体能在 AI 原生架构里继续存活下去的关键适配。

本体作为承载体，从来没有真正「消失」—— 它只是从推理链条的终点（产出真理），退到了推理链条的入口（供给上下文）。

一个可操作的判据 判断一个系统是「经典本体驱动」还是「Palantir 式混合驱动」，不要看它是否画了 Object / Property 图谱，而要看推理结果的最终责任人是推理机、检索引擎，还是 LLM。 这个责任归属点，才是两种范式真正的分水岭。

数据与语义的落地细节

  • 数据映射：把数据库表 / API / 文件映射成 Object Type 和 Property，是「物理世界」到「语义世界」的入口。

自研框架 · 非 Palantir 官方

Chapter 06 · 独立章节一套自研的本体建模规范：从三模型到十一大模型

本章说明 本章介绍的建模规范，是参考文章作者「人月聊IT」个人自研的框架，不是 Palantir 官方方法论，也不是 W3C 标准。它参考了 Palantir 本体建模、经典本体论建模（OWL / OOAD），并结合作者本人一年多的实际项目反复迭代而成。 原作者自述：「这套规范是我过去一年多在 actual 项目中不断迭代出来的，它不一定完美，但确实是『用过、踩过坑、改过』的东西。」规范已开源：github.com/sharptoolbox

之所以单独成章完整收录，是因为它提供了一个从工程视角补齐 Palantir 未展开部分的完整样本：Palantir 讲了「本体能做什么」，这套规范讲了「一个 AI 原生系统的本体到底该由哪些模型组成」。

缘起：传统需求文档太「扁平」

传统需求文档能说的它说不出来的
系统要做什么业务对象之间到底是什么关系
有哪些功能一个操作发生后会触发什么连锁反应
输入输出是什么哪些规则是跨对象的、哪些是局部的
—系统边界的接口契约是什么

目标因此定为三条：能承载经典本体论的语义严谨性；能对接实际的软件工程实践；能被 AI 理解并执行。

六个版本的演进

V1

三模型：对象 · 行为 · 规则

M1 对象模型覆盖实体、属性、关系、约束 —— 基本对应 OWL / OWL 2 的核心。关键理念：描述的是「业务对象」，不是「数据库表」。建模时不要想表怎么拆，先想把业务搞清楚；表拆分交给后面的 MM 映射模型。
M2 行为模型是「领域行为」而不是 CRUD：「确认支付」「提交合同」「激活客户」。每个行为有原子性、前后置条件、规则引用、事件产生。
M3 规则模型可映射到 Function，但区分两层：简单约束（OWL 能表达）与复合规则（如「合同所有开票金额之和 = 合同总金额」，需 SWRL / SHACL 级表达力）。

V2

事件模型 + 对象模型升级为 DDD 领域对象

对象引入 DDD 分类：聚合根（业务完整性边界，全局唯一标识）、实体（聚合内子对象，聚合内唯一标识）、值对象（无标识不可变）。订单 + 订单明细是同一聚合；订单 + 客户是独立聚合 —— 这个区分直接决定事务边界在哪里。
ME 事件模型用消息中间件机制解耦：「确认支付」成功后不直接调用「扣减库存」，而是发布 Order.PaymentConfirmed，库存模块订阅后自行决定。事件模型还有一个实用场景：作为大模型「思考链」中的标准化节点 —— 每完成一步推理就发布一个事实事件。

V3

场景模型 + 主体模型

M4 场景模型核心思路类似 SOA：任何业务问题就是一个场景，由跨对象的行为与规则灵活组合编排去解决。它回答的是「你整个本体模型究竟怎么用」。在 Palantir 里对应 What-if 假设分析与基于分析完成的 Workflow 定义。
M5 主体模型定义参与者、角色、权限边界。看起来传统，但有特殊定位：它是一个横切层，贯穿 L1 到 L6 —— 行为要声明所需权限、流程人工活动要引用审批角色、UI 元素要控制可见性，全部指向 M5。

V4

流程模型 + 查询统计与报表模型

M6 流程模型从场景模型里拆出来，因为审批流有自己特点：人工参与、退回驳回、角色泳道、网关分支。它统一承载两类流程 —— COLLABORATION（端到端业务协同流）与 APPROVAL（审批流）。
M7 查询统计与报表模型遵循读写分离原则：只与 M1、M2 直接关联，不引用 M3 / ME / M4 / M5 / M6。目的是避免把复杂查询逻辑塞进原子行为或业务规则里。

V5

映射模型 + UI 模型

MM 对象-数据表映射模型解决遗留系统问题：聚合根 → 主表，子实体 → 从表，值对象 → 主表字段平铺或 JSON 列，复合对象 → 一对多映射到多张表。职责边界：MM 只表达对应关系，索引、分区、迁移脚本不进入 MM。
MU UI 模型承担特殊角色：入口层 + 全链路追溯层，定义了从用户点击到系统完成的完整调用链。

V6

接口模型 —— 十一大模型完整版

MI 接口模型把系统边界两侧的接口契约独立成模：名称、方向（提供方 / 依赖方）、输入参数、输出格式、返回规则。它只描述契约，不承载行为执行语义或事件投递语义 —— 接口的原子执行由 M2 的 triggerType=EXTERNAL 行为承接，MI 与这些模型通过稳定 ID 双向引用。

MU 定义的完整调用链

用户操作（屏幕 / 元素 / 事件）
  → VALIDATE                    （M3 规则，UI 前置校验）
  → BEHAVIOR_CALL               （M2 行为，操作 M1 对象）
  → EVENT_EMIT                  （ME 事实事件）
  → SCENARIO_CALL               （M4 跨对象协同）
  → REPORT_CALL / QUERY_REPORT  （M7 输出）
  → NAVIGATE                    （MU 屏幕跳转）

这意味着：从用户点击一个按钮开始，到系统完成所有处理，整条链路都是可追溯的。每个实现单元都可以溯源到具体的本体模型定义。

Chapter 07项目实践

需求探索：怎么问出一个本体

核心难点：业务方不会用本体的语言跟你说话。基本流程是把「业务口语」逐层翻译成「模型元素」：

业务访谈（口语） → 场景识别 → 业务场景清单
                 → 概念抽取 → 业务概念与术语表
                 → 关系与约束梳理 → 对象 / 关系 / 规则候选集
                 → 完整性判定 → 结构化需求文档 + 本体模型草稿

一个实用的提问框架 —— 把「功能」问题改造成「本体」问题：

不要问要问
这个系统有哪些功能？这个业务里有哪些东西（对象）？
用户怎么操作？谁能对这些东西做什么动作？
有什么业务规则？做这个动作之前必须满足什么？做完之后什么会变？
有什么流程？一个动作发生后，谁会跟着动？（事件链）
报表要什么字段？你要回答的是什么问题？（读模型反推）

完整性判定自检

  • 每个对象都有明确的标识吗？（Primary Key / 聚合根）
  • 每个对象都能在图上连到至少两条边吗？（只连一条边的，多半是分类节点）
  • 每个行为都有前置条件和后置状态变化吗？
  • 每条规则引用的是哪些对象？跨对象的规则找出来了吗？
  • 有没有孤岛（某个对象谁都不引用）和断头路（某个行为没有任何触发来源）？

知识萃取：把老师傅的脑子掏出来

这是整个项目里最难、最不可替代、也最容易被低估的一环。核心命题：企业私有业务经验不显性化，本体模型就是空壳。

层抽取什么例子
场景层业务在什么情况下会面对什么问题「关键物料供货中断」
概念层这个问题涉及哪些业务概念替代物料、安全库存、调货
实体层具体的数据与对象实例物料 #M-1024、供应商 #S-08

两轮萃取法：

  1. 第一轮 · 广撒网。让专家描述「你平时怎么处理这类问题」，不打断、不纠正，记录完整叙述。
  2. 第二轮 · 逼边界。针对第一轮里的每一个判断点追问：「什么情况下你会不这么做？」「如果 XXX 发生变化，你的做法会变吗？」「你怎么知道这个判断是对的？」
关键认知 第一轮产出的是故事，第二轮产出的是可执行的决策规则 —— 第二轮才是产出规则的地方。 AI 推理不能天马行空，必须基于已有的方法和认知框架约束。没有这个框架，AI 就是瞎推理 —— 虽然能得出结论，但可能严重脱离企业实际，置信度极低。

面组成职责
控制面约 10 个模块定义、配置、编排、治理、监控 —— 决定「做什么」
执行面约 18 个引擎实际执行计算、检索、推理、调用 —— 负责「做出来」

三个关键机制：

  • 能力注册表：所有可用能力（Function、查询、外部接口）在此登记，供编排层发现和调用；
  • 场景配方库：把验证过的场景解法沉淀成可复用的「配方」；
  • 执行计划 DAG：单条执行计划内部不允许有环；长期回路放在事件总线上 —— 这是保证系统可终止、可调试的关键设计。

五个案例

案例 01 · 供应链

库存周转率预警与决策回写

做法两步：① 传统部分 —— 采集多方数据 → ODS → 宽表 → 指标计算（数据中台即可完成）；② 本体部分 —— 执行动态模型 → 触发动态计算 → 形成回写策略回写采购系统。

模拟三种决策意见：引入替代物料 / 调货 / 调整安全库存。实际场景中由人工审阅三种方案后选一条最优决策回写。

关键：回写本身没有技术含量，重点是「模型 + 数据 + 大模型推理 → 得出比有经验员工更优的改进建议」。

案例 02 · 电商

自动化运营与「举一反三」

客户困惑：我们已经用 AI + 精确代码实现了自动化推荐、自动补货，那本体论还有什么用？

把问题反过来问：自动化运营涉及补货、调货、预警、客服、推荐、数据分析……是不是每出现一个新场景，你都要新开发一个代码程序？

目标：给 AI 列举 5 到 10 种已有场景的做法后，AI 能基于底层对象模型与行为规则，自动推理出新场景的应对方法。这才是举一反三。

案例 03 · 物流

经营分析原型

指标异常告警 → 沿本体关系上溯定位异常对象（哪条线路、哪类货品、哪个客户）→ 沿链路回溯定位具体行为 / 事件过程 → 在沙箱中模拟不同调整策略 → 输出可解释的归因结论与改进建议。

原作者强调：「从结果追溯到过程」还不够，还要能回答「我该如何解决」。要的是改进建议，而不是仅仅知道问题本身。

案例 04 · 企业架构

架构文档 → 本体模型

输入：企业架构文档、业务需求文档等非结构化资料。

过程：知识抽取 → 场景 / 概念 / 实体三层建模 → 与既有数据库勾稽。

输出：覆盖 LTC（线索到现金）等端到端流程的本体模型。把散落在文档里、从未被结构化表达的流程知识，变成 AI 可推理的语义网络。

案例 05 · 合同 / 制造

规则模型的典型战场

· 「合同所有开票金额之和 = 合同总金额」—— 跨对象的复合约束
· 「累计收款达到合同总额时自动关闭合同」—— 事件驱动规则
· 「批次质量不合格时触发召回流程」—— 事件链 + 流程模型

五条红线

做本体 + AI 分析推理的项目，这五条必须在设计阶段就写死：

01
LLM 不生成数字，只引用数字数字必须来自确定性计算，LLM 只做组织与表达
02
本体要精确，但不必完备追求完备会陷入无限建模；够用即可迭代
03
SQL 可溯源每一个数字都要能追到它的查询语句
04
推理过程透明用户要能看到 AI 是怎么一步步得出结论的
05
降级策略明确，不做 Mock能力不可用时明确降级并告知，绝不伪造结果
第 5 条尤其重要 宁可告诉用户「这个能力暂时不可用」，也不要返回一个看起来合理但是编的答案。在企业场景里，一次伪造的结论比十次「不可用」的破坏力大得多。

三层公式

可靠的数据分析报告
= 确定性计算 ＋ 语义锚定 ＋ 开放推理
SQL + 统计算法

负责数字准确。缺了它，数字靠不住，报告不可信。

本体模型

负责概念不歧义、对象不指错。缺了它，算得对但指错了东西。

LLM

负责归因、类比、常识补全、生成表达。缺了它，只有数据没有洞察。

与之配套的还有一句架构原则：「降级和编排，而不是抛弃。」当某一层能力不足时（比如没有可用的图数据库），降级到上一层能用的机制，而不是把整个方案推倒重来。

常见失败模式

失败模式症状根因
建成了目录树模型是一级分类 → 二级分类 → 三级分类没有识别对象之间的相互约束关系
只建了名词有对象、有关系，没有行为、事件、场景漏掉了「过程」，模型无法运转
规则全塞进行为每个行为里一堆 if-else没有独立的规则模型
查询逻辑污染写模型为了报表改了核心业务规则没有读写分离
权限事后补上线前才发现要加权限主体模型没有作为横切层
本体和系统两张皮模型很漂亮，系统完全不按模型跑缺少 MM 映射 / MU 调用链
AI 无约束推理结论漂亮但脱离实际没有把经验显性化为认知框架
追求完备建模半年还没上线违反了「精确但不必完备」

六条学习路线

不同角色看到的是同一套东西的不同侧面。选一条主线，其余作为补充：

十个常见误区

  1. 把本体当成知识图谱。本体是 TBox（模式），知识图谱是 ABox（实例）。画了一堆实例不等于是本体。
  2. 把本体建成目录树。树状结构用传统 OO 建模就够了，不需要本体。
  3. 用 OWL / SWRL / SHACL 去逆向解释 Palantir。方法论上的时代错位 —— 两者是不同认识论立场的分岔。
  4. 以为 Palantir 要替换现有系统。它是「水的搬运工」，最大化保留你已有的 IT 资产。
  5. 以为回写是重点。回写没有技术含量；「得出比有经验员工更优的建议」才是。
  6. 以为模型建好 AI 就能自主决策。企业私有经验不显性化，模型代替不了业务专家。
  7. 以为本体要建得完备才能用。精确但不必完备 —— 完备是建模者的执念，不是业务的需求。
  8. 只建名词不建动词。没有行为、事件、场景，模型无法运转，AI 也推理不出东西。
  9. 让 LLM 生成数字。数字必须来自确定性计算，LLM 只做组织与表达。
  10. 能力不可用时返回编造的答案。明确降级并告知，绝不 Mock。

自检清单

评估一个本体模型（建得对不对）

  • 是网状而不是树状吗？对象之间有相互约束回路吗？
  • 每个对象都有明确标识吗？有没有孤岛对象和断头路行为？
  • 行为有前置条件和后置状态变化吗？还是只是 CRUD？
  • 规则里有没有跨对象的复合规则？行为与事件拆开了吗？
  • 场景是显式建模的，还是留给 AI 自己发挥的？
  • 权限是横切在模型里的，还是事后补的？

评估一个本体项目（该不该做）

  • 这个痛点是传统 IT 应用难以解决的吗？
  • 是 AI 因为幻觉太重而无法满足的吗？是极度依赖有经验员工的吗？
  • 这个场景允许不确定性和一定置信度吗？是多目标平衡而非单目标最优吗？
  • 企业的业务经验能被显性化吗？谁来做这件事？
如果以上大部分是「否」 那这个问题可能不需要本体 —— 用精确的程序代码就能解决。这是完全正确的结论，不要硬上本体。

最后三句话

一、本体论不是万能的。很多精确化的问题不需要本体就能很好地解决。

二、本体 + AI 一定不能是无中生有，只能是举一反三。你给出足够的经验积累，AI 才能自主推理。

三、本体没有消失，它只是从推理链条的终点退到了入口。这个角色迁移，正是本体论在 AI 原生架构里继续存活、而不是被 LLM 完全取代的关键路径。
